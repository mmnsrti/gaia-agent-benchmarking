# V5 — One-Shot Post-Answer Verification

Status: FROZEN

Branch: `v5-one-shot-verification`

Parent Baseline: Frozen V4 (`v4-planner-router-final`)

---

## 1. Research Definition & Capability Boundary

```text
V5 = frozen V4 + one-shot conservative post-answer verification/revision
```

The primary research question evaluated by V5 is:
> *Does adding an explicit, conservative one-shot post-answer verification and revision stage improve candidate answers already generated by the frozen V4 capability-routing pipeline?*

Secondary research question:
> *Can a conservative KEEP-biased verifier correct formatting, extraction, or superficial reasoning mistakes without introducing destructive regressions on already-correct candidate answers?*

### What V5 Does NOT Test
V5 evaluates strictly a single-shot, text-only post-answer inspection. It explicitly does **NOT** test:
- Iterative reflection or multi-turn agent deliberation
- Multi-step self-correction or search loops
- Active verification tools (e.g. test execution, sandbox re-runs, or new queries)
- Recovery solving on upstream failures or empty candidate answers
- Query rewriting or multi-hop web retrieval
- Autonomous replanning or tool calling

## 2. Execution Flow & Architecture

```text
GAIA Question + Optional Attachment File
     ↓
ONE Tavily Search (Original Question as Query, Capped at 1,500 Chars, N ≤ 1)
     ↓
FileTool (Deterministic local extraction inherited from frozen V2/V3/V4, N ≤ 1)
     ↓
Stage 1: Frozen V4 Router Generation (`capability-router-v1`, mode="NONE", N ≤ 1)
     ↓
Deterministic Route Parser (Regex validation, deterministic fallback to DIRECT)
     ↓
Stage 2: Route-Specific Worker Dispatch (`router-direct-worker-v1` or `router-python-worker-v1`, mode="NONE", N ≤ 1)
     │
     ├── [Route == DIRECT] → Generates direct response text (`FINAL: <answer>`)
     │
     └── [Route == PYTHON] → Emits ```python code block executed in local sandbox
                             (Timeout 15.0s, Cap 20k chars, Static AST Validation, N ≤ 1)
     ↓
Candidate Answer Extraction (`pre_verification_answer`)
     ↓
Candidate Eligibility Guard
     ├── [Empty Candidate / Upstream Failure]
     │        ↓
     │   Verifier Bypassed Immediately (0 verifier LLM calls, preserves empty failure safety)
     │        ↓
     │   Final Answer = Empty / Upstream Output
     │
     └── [Candidate Present (Non-Empty)]
              ↓
         Stage 3: One-Shot Verifier Generation (`answer-verifier-v1`, mode="NONE", N ≤ 1)
         (Inputs: Question, Attachment Summary/Bytes, Search Results, Candidate Answer)
              ↓
         Deterministic Verdict Parser (`VERDICT: KEEP` or `VERDICT: REVISE with FINAL: <answer>`)
              ├── [Verdict == KEEP] → Post-Verification Answer = Candidate Answer (100% preservation)
              ├── [Verdict == REVISE] → Post-Verification Answer = Revised Answer
              └── [Verifier Failure / Error] → Fallback preserves Candidate Answer identically
              ↓
         Final Answer
```

### Key Architectural Behaviors
1. **Empty Candidate Bypass**: If the upstream worker fails to produce a candidate answer (e.g. execution timeout, AST rejection, empty response, or provider anomaly), the verifier is bypassed immediately. No LLM call is made, preserving empty-candidate failure safety.
2. **Failure-Safe Preservation**: On any verifier parsing failure, provider timeout, or malformed verdict, the verifier deterministically falls back to preserving the upstream candidate answer without modification.
3. **Strict No-Retry Invariant**: The verifier runs at most once per task ($N \le 1$). There are no repair loops, iterative retries, or re-verification attempts.

## 3. Strict Frozen Invariants

The V5 architecture strictly enforces the following invariants:
- **Search Count**: At most 1 Tavily search execution per task ($N \le 1$).
- **FileTool Invocations**: At most 1 FileTool execution per task ($N \le 1$).
- **Python Executions**: At most 1 Python subprocess execution per task ($N \le 1$).
- **Router Generation**: Exactly 1 router generation attempt per task ($N \le 1$).
- **Worker Generation**: Exactly 1 worker generation attempt per task ($N \le 1$).
- **Verifier Generation**: At most 1 verifier generation attempt per task ($N \in \{0, 1\}$).
- **Total LLM Generation Cap**: Maximum 3 LLM generation attempts per task across the entire pipeline.
- **Route Enforcement**: Tasks routed to `DIRECT` cannot invoke Python.
- **Passive Verifier Scope**: The verifier has no tool access, cannot invoke Python, cannot execute web searches, and cannot call external APIs.
- **No Iterative Loops**: No multi-turn self-correction, reflection loops, or autonomous agent cycles.
- **KEEP Invariant**: A `KEEP` verdict must preserve the upstream candidate answer identically.
- **Fallback Invariant**: Verifier errors, timeouts, or malformed outputs must preserve the upstream candidate answer identically.
- **Native Function Calling Disabled**: Router, workers, and verifier all run with Gemini native function calling disabled (`mode="NONE"`).

## 8. Matched-Control Interpretation

It is vital to distinguish between two separate V4 results documented in this repository:
1. **Historical Frozen V4 Canonical Result**: **52 / 165 (31.52%)**, established during the V4 freeze (`experiments/v4/`).
2. **Contemporaneous Matched V4 Control**: **57 / 165 (34.55%)**, executed alongside V5 under identical environment conditions during the V5 experimental campaign (`experiments/v5_matched_v4/`).

The 57/165 matched control does **NOT** replace the historical frozen V4 canonical baseline. It serves as the contemporaneous control for the V5 campaign.

### Cross-System Transitions
Between the separate matched V4 and V5 runs:
- **Both Correct**: 42 tasks
- **Both Wrong**: 97 tasks
- **V4 Wrong → V5 Correct (Observed System Improvement)**: 11 tasks
- **V4 Correct → V5 Wrong (Observed System Regression)**: 15 tasks
- **Observed Net Difference**: $11 - 15 = -4$ tasks (-2.42 pp)
- **Sum Identity**: $42 + 97 + 11 + 15 = 165$ tasks.

The observed V5-vs-matched-V4 difference arose across separate stochastic runs and should not be attributed to any single mechanism without stronger causal evidence. This cross-run difference may reflect upstream stochastic variation, including differences in routing, worker generation, retrieval outputs, provider behavior, and execution outcomes.

## 9. Failure Mechanism Summary

Across the 112 tasks where V5 was scored incorrect:
- **Category A: Missing Candidate / Upstream Failure (84 / 112 = 75.00%)**:
  - Provider-reported `MALFORMED_FUNCTION_CALL` finish-reason anomaly on Python workers: 76 tasks.
  - Python sandbox execution failure or missing answer marker: 6 tasks.
  - Empty worker responses: 2 tasks.
  - *Effect*: Three-quarters of all failures occurred upstream of the verifier, starving the verification stage of candidate answers.
- **Category B: Completed Candidate Incorrect (28 / 112 = 25.00%)**:
  - Verifier issued KEEP (preserving incorrect candidate): 26 tasks (92.86% of wrong candidates).
  - Verifier issued REVISE (revised answer remained incorrect): 2 tasks (7.14% of wrong candidates).
- **Attachment Difficulty**: 32 of 38 attachment tasks failed (84.21%), concentrated in `.xlsx` (12/13), `.png` (8/8), `.mp3` (2/3), and `.zip` (2/2).

## 11. Limitations

1. **Separate Stochastic Runs**: The comparison between V5 and matched V4 was conducted across separately executed runs under the provider-default sampling configuration (where temperature was not explicitly fixed by project configuration), introducing run-to-run sampling variance.
2. **Level 2 Delay Discrepancy**: V5 Level 2 ran with a 1.0s inter-task delay, whereas matched V4 Level 2 ran with a 5.0s delay. No operational degradation attributable to the timing difference is evident in the recorded telemetry; however, the runs were not identical in inter-task throttling. Classified as a non-blocking comparability limitation.
3. **Provider Finish-Reason Anomalies**: Upstream Python workers frequently encountered `MALFORMED_FUNCTION_CALL` finish reasons despite function calling being disabled, causing 76 tasks to produce no candidate answer and constricting the verifier eligibility pool.
4. **Candidate Starvation**: 84 / 165 tasks (50.91%) produced no candidate answer, preventing verifier evaluation on more than half the benchmark.
5. **Limited REVISE Sample**: Only 3 tasks received REVISE verdicts, limiting statistical observations of revision behavior.
6. **Passive Text-Only Scope**: The verifier operated solely on static text without tool access, code execution, or targeted search capabilities.

## 12. Scientific Conclusion

In the canonical V5 run, one-shot conservative post-answer verification produced zero improvements and zero regressions under the official GAIA scorer, leaving accuracy unchanged at 53/165.

1. **Conservative Failure Safety**: The V5 post-answer verification stage demonstrated conservative failure safety, achieving zero regressions ($1 \rightarrow 0$) and zero corruption of valid candidate answers across all 165 tasks.
2. **Empirical Verification Neutrality**: The conservative verification mechanism produced no empirical accuracy gain ($\Delta = 0.00\text{ pp}$ within V5), with the verifier accepting 92.86% of incorrect candidates that reached it, alongside significant upstream candidate starvation (50.91% empty candidates).
3. **Cross-Run System Comparison**: V5 as a complete system solved 53/165 tasks versus 57/165 for the contemporaneous matched V4 control; because these were separate stochastic runs, this comparison does not isolate a pure causal verifier effect. The observed difference may reflect differences in routing, worker generation, retrieval outputs, provider behavior, and execution outcomes.
4. **Configuration-Bounded Finding**: In this V5 configuration, a single conservative text-only post-answer verifier did not improve official GAIA accuracy. While passive post-answer verification preserved existing correct answers, it did not resolve errors on incorrect candidate answers in this evaluation.

Future versions may test verification mechanisms with additional evidence-gathering, execution, or targeted re-checking capabilities.
